## Clarifications

### Session 2026-07-25

- Q: API キーの受け渡し方法は？ → A: `Authorization: Bearer <key>` ヘッダで送る
- Q: Todo の `id`（一意識別子）の形式は？ → A: UUID
- Q: `description`（説明）の最大長は？ → A: 1024 文字
- Q: 認証の位置づけは？ → A: P1 に昇格。全エンドポイントで最初から必須（MVP に含む）
- Q: 作成（POST）時に `completed` を指定できるか？ → A: 不可。作成時は常に `false`、変更は更新（PUT）でのみ
- Q: 一覧（GET /todos）のデフォルト並び順は？ → A: 作成日時の降順
- Q: バリデーションエラーで不正項目を示すか？ → A: 示す（機能要件に昇格）

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー 1 - TODO を CRUD で管理する (優先度: P1)

利用者は、やるべきこと（TODO）を登録し、一覧や個別に確認し、内容を書き換え、不要になったら削除できる。これにより、タスクの記録と進捗管理を 1 つの API で完結できる。

**この優先度の理由**: TODO を作成・参照・更新・削除できることが本 API の中核価値であり、これ単体で「タスクを管理する」という実行可能な MVP になる。

**独立テスト**: 有効な API キーを持つクライアントから作成→一覧→取得→更新→削除の一連の操作を実行し、各操作が期待どおりの結果とステータスを返すことで完全にテスト可能。認証（US2）と併せて MVP を構成する。

**受け入れシナリオ**:

1. **Given** 認証済みの利用者, **When** `title` を指定して TODO を作成する, **Then** 201 と作成された TODO（`id`・各属性・作成日時を含む）が返る
2. **Given** `title` を指定しない, **When** TODO を作成する, **Then** 400 とどの項目が不正かを示すバリデーションエラーが返る
3. **Given** `title` が 256 文字を超える, **When** TODO を作成する, **Then** 400 とバリデーションエラーが返る
4. **Given** `completed` に `true` を含めて作成する, **When** TODO を作成する, **Then** `completed` は無視され `false` の TODO が作成される
5. **Given** 既存の TODO が複数ある, **When** 一覧を取得する, **Then** 200 と全 TODO が作成日時の降順（新しい順）で返る
6. **Given** 存在する `id`, **When** 個別に取得する, **Then** 200 と該当 TODO が返る
7. **Given** 存在しない `id`, **When** 個別に取得する, **Then** 404 が返る
8. **Given** 既存の TODO, **When** 全項目（`completed` を含む）を指定して更新する, **Then** 200 と更新後の TODO（`updated_at` が更新済み）が返る
9. **Given** 存在しない `id`, **When** 更新する, **Then** 404 が返る
10. **Given** 既存の TODO, **When** 削除する, **Then** 204 が返り、以後その `id` を取得すると 404 が返る

---

### ユーザーストーリー 2 - API キーで全エンドポイントを保護する (優先度: P1)

すべてのエンドポイントは API キーによる認証を要求し、正しいキーを提示したリクエストのみを処理する。これにより、権限のない第三者による TODO データの参照・改変を防ぐ。

**この優先度の理由**: データ保護の基本要件であり、認証なしにデータ操作 API を公開してはならない。CRUD（US1）と併せて最初から必須の MVP 要件とする。

**独立テスト**: 有効なキー・無効なキー・キー無しの 3 パターンで任意のエンドポイントを叩き、有効時のみ処理され、それ以外は 401 で拒否されることを確認する。

**受け入れシナリオ**:

1. **Given** 有効な API キーを `Authorization: Bearer <key>` で提示する, **When** 任意のエンドポイントにアクセスする, **Then** リクエストが正常に処理される
2. **Given** `Authorization` ヘッダを付けない, **When** 任意のエンドポイントにアクセスする, **Then** 401 が返り、処理は行われない
3. **Given** 不正な API キーを提示する, **When** 任意のエンドポイントにアクセスする, **Then** 401 が返り、処理は行われない

---

### エッジケース

- リクエストボディが不正な形式（壊れた JSON など）の場合は 400 を返す
- `title` が空文字または空白のみの場合はバリデーションエラー（400）とする
- 未知の属性を含むリクエストは、その属性を無視して処理する（エラーにはしない）
- 一覧取得時に TODO が 1 件も無い場合は、200 と空配列を返す（404 ではない）
- 更新・削除で対象 `id` が存在しない場合は一貫して 404 を返す

## 要件 *(必須)*

### 機能要件

- **FR-001**: システムは、利用者が新しい TODO を作成できる機能を提供しなければならない (MUST)
- **FR-002**: システムは、`title`（必須・1〜256 文字）と `description`（任意・最大 1024 文字）を受け付けなければならない (MUST)
- **FR-003**: システムは、`title` が未指定・空・256 文字超のリクエストを拒否し、バリデーションエラーを返さなければならない (MUST)
- **FR-004**: システムは、登録済み TODO の一覧を作成日時の降順（新しい順）で取得できる機能を提供しなければならない (MUST)
- **FR-005**: システムは、`id` を指定して単一の TODO を取得できる機能を提供しなければならない (MUST)
- **FR-006**: システムは、`id` を指定して TODO の全項目を更新できる機能を提供しなければならない (MUST)
- **FR-007**: システムは、`id` を指定して TODO を削除できる機能を提供しなければならない (MUST)
- **FR-008**: システムは、存在しない `id` への取得・更新・削除に対して「未検出」を示す応答を返さなければならない (MUST)
- **FR-009**: システムは、各 TODO に一意な識別子（`id`、UUID 形式）と、作成日時・更新日時を自動的に付与しなければならない (MUST)
- **FR-010**: システムは、`completed`（完了フラグ）を保持しなければならない。作成時は常に `false` とし、作成リクエストで `completed` が指定されても無視する。値の変更は更新（PUT）でのみ行える (MUST)
- **FR-011**: システムは、すべてのエンドポイントで API キー認証を要求しなければならない (MUST)
- **FR-012**: システムは、API キーが未提示または不正なリクエストを拒否し、認証エラーを返さなければならない (MUST)
- **FR-013**: システムは、データを永続化し、再起動後もデータが失われないようにしなければならない (MUST)
- **FR-014**: システムは、バリデーション違反時に、どの項目がなぜ不正かを示す情報を応答に含めなければならない (MUST)

### 主要なエンティティ *(機能がデータを扱う場合に含める)*

- **Todo**: 利用者が管理する 1 件のタスク。主要な属性: 一意な識別子（`id`、UUID）、`title`（タイトル・1〜256 文字）、`description`（説明・任意・最大 1024 文字）、`completed`（完了状態）、作成日時、更新日時。

## 成功基準 *(必須)*

### 測定可能な成果

- **SC-001**: 正常な CRUD 操作（作成・一覧・取得・更新・削除）が、それぞれ仕様どおりのステータスと内容を 100% 返す
- **SC-002**: API キーが無い、または不正なリクエストは 100% 拒否される
- **SC-003**: バリデーション違反（title 欠落・長さ超過・空）のリクエストは 100% 拒否される
- **SC-004**: 作成した TODO は、システム再起動後も取得でき、データ損失が発生しない
- **SC-005**: 存在しない `id` への操作は、取得・更新・削除のいずれでも一貫して「未検出」を返す

## 前提

- 利用者（クライアント）は単一の信頼された呼び出し元を想定し、マルチテナントや利用者ごとの認可はスコープ外とする（API キーは単一）。
- 一覧のページング・検索・フィルタ、および部分更新（PATCH）は本バージョンのスコープ外とする。
- リクエスト/レスポンスの形式は JSON を前提とする。
- 同時実行や大量データに対する性能目標は本バージョンでは定めない（サンプル用途）。
